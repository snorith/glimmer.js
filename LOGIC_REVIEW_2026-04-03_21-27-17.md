# Logic Review Report: Glimmer.js Runtime
**Date:** 2026-04-03
**Scope:** `glimmer.js` (Core Runtime)

### 1. Overview
The `glimmer.js` runtime is a fork optimized for a specific standalone usage pattern. While it successfully decouples from the full Ember infrastructure, it inherits and introduces several logical constraints related to global state management, revalidation timing, and error handling. The core architecture relies on a singleton `RenderManager` which, while encapsulated in a class, still effectively functions as a global state container for all Glimmer components in a given JS environment.

---

### 2. Findings by Module/File

#### A. `packages/@glimmer/core/src/render-component/index.ts`

| Finding | Reference | Criticality |
|:---|:---|:---|
| **Singleton Render Manager** | `MANAGER` (Line 138) | **Medium** |
| **Atomic Revalidation Loss** | `scheduleRevalidate` (Lines 100-117) | **Low** |
| **`didRender` Timing Drift** | `didRender` (Lines 128-135) | **Medium** |

*   **Singleton Render Manager:** The `MANAGER` constant is a module-level instance of `RenderManager`. This prevents true isolation between multiple Glimmer-based widgets or applications running on the same page if they are loaded from the same bundle. They will share a single revalidation loop and re-render concurrently, which may lead to unexpected interleaving of lifecycle hooks across separate apps.
*   **Atomic Revalidation Loss:** If `scheduleRevalidate` is called while `scheduled` is true, the call is ignored. While this is intended to debounce renders, if a tracked change occurs *during* the revalidation phase but after a specific component has already been checked, that component might remain stale until the *next* unrelated change triggers another render.
*   **`didRender` Timing Drift:** The `didRender` promise only waits for the *currently* scheduled render. If a render is in progress and schedules *another* render (e.g., via a side effect), the promise from the first call might resolve before the second render completes, leading to race conditions in tests or async logic that depends on the DOM being fully stable.

#### B. `packages/@glimmer/core/src/environment/delegates.ts`

| Finding | Reference | Criticality |
|:---|:---|:---|
| **Synchronous Destruction Side-effects** | `onTransactionCommit` (Line 98) | **Medium** |
| **Global State for Destructions** | `scheduledDestructions` (Line 10) | **Medium** |

*   **Synchronous Destruction Side-effects:** Destructors are called immediately during `onTransactionCommit`. If a destructor modifies tracked state (which is discouraged but possible), it can trigger a new revalidation cycle immediately or cause "update after use" errors in the middle of a teardown, potentially leaving the system in an inconsistent state.
*   **Global State for Destructions:** Like the Render Manager, `scheduledDestructions` and `scheduledFinishDestruction` are module-level globals. This further breaks multi-app isolation, as one app committing a transaction will trigger destructions for *all* apps in the same environment.

#### C. `packages/@glimmer/tracking/src/tracked.ts`

| Finding | Reference | Criticality |
|:---|:---|:---|
| **Error Message Mutation** | `descriptorForField` (Lines 140-146) | **Low** |

*   **Error Message Mutation:** In `DEBUG` mode, errors thrown during property access are caught, modified to include the class and property name, and re-thrown. While helpful for debugging, this can break logic that relies on specific error types (e.g., `instanceof`) or patterns in error messages, and it may fragment stack traces in certain environments.

---

### 3. Root Cause Analysis
1.  **Singleton Bias:** The architecture assumes a "Primary App" model where all Glimmer components belong to a single logical hierarchy managed by one renderer.
2.  **Implicit Batching:** The `setTimeout(..., 0)` strategy for revalidation is a simple way to batch changes but lacks the robustness of a dedicated scheduler (like the one found in Ember or React) that can handle priorities and nested updates.
3.  **Loose Encapsulation:** Variables like `scheduledDestructions` were moved outside the class to satisfy specific import patterns or legacy VM requirements, leading to "leaky" global state.

---

### 4. Suggested Fixes

1.  **Context-Aware Rendering (High Priority):**
    Refactor `renderComponent` to allow passing a specific `RenderManager` instance or use a `WeakMap` to associate elements/roots with their respective managers. Remove the global `MANAGER` singleton.
2.  **Revalidation Guard (Medium Priority):**
    In `RenderManager.revalidate()`, check if new changes were tracked *during* the loop and optionally perform a second pass (with a limit) to ensure convergence.
3.  **Localized Destruction (Medium Priority):**
    Move `scheduledDestructions` into the `BaseEnvDelegate` instance rather than the module scope. Ensure `EnvironmentDelegate` is the source of truth for its own destruction queue.
4.  **Preserve Error Types (Low Priority):**
    Instead of re-throwing a modified error message, wrap the original error in a custom `GlimmerError` that preserves the original error object as a property (e.g., `error.cause`).

---

### 5. Criticality Rating

*   **High:** None identified that cause immediate data corruption.
*   **Medium:** Singleton `RenderManager` and global destruction queues (prevents clean multi-app isolation and causes cross-talk during teardown).
*   **Low:** `didRender` timing drifts and error message formatting.
